# 企业知识库生产环境配置说明

> 本手册是单机生产 Compose 的批准操作路径。不要把开发 `.env`、
> `docker compose up -d`，或 Helm 示例当作生产部署方法。

## 1. 适用范围

本手册适用于部署在企业内网的一台 Docker Compose 主机：一个 App 容器、
PostgreSQL、Redis、DocReader 和前端运行在 Compose 中，Ollama 是外部内部服务。
它不适用于多 App 副本、公开互联网直连服务，或未完成 API/Worker 拆分的集群部署。

## 2. 上线前条件

- 主机至少 8 核 CPU、16 GB 内存；Ollama 的 CPU、内存或 GPU 容量另行预算，不计入此基线。
- 已安装 Docker Engine 和 Docker Compose v2。
- 企业 HTTPS 反向代理、可用的备份目录和内部 DNS 已准备完毕。
- 已确定外部 Ollama 的内部地址、可用模型和容量负责人。
- 已准备实际且未被 Git 跟踪的 `deploy/production/.env.production`。不要提交该文件或其中的任何秘密。

## 3. 环境文件

从模板创建生产变量文件，并在受控的秘密管理流程中编辑它：

```bash
cp deploy/production/.env.production.example deploy/production/.env.production
```

必须替换模板中的 `DB_PASSWORD`、`REDIS_PASSWORD`、`JWT_SECRET`、
`SYSTEM_AES_KEY` 和 `TENANT_AES_KEY`，以及实际使用的模型、对象存储和第三方数据源凭证。
不要把真实值写入本文档、示例文件、Shell 历史或 Git。

`JWT_SECRET`、`SYSTEM_AES_KEY`、`TENANT_AES_KEY` 是上线后必须保持稳定的三项密钥：
生成后保存到企业秘密库，在重启、升级、回滚和恢复时使用同一组值。尤其不能丢失或随意轮换
`SYSTEM_AES_KEY`、`TENANT_AES_KEY`，除非执行单独的密钥迁移。

所有生产操作都使用这个真实且未跟踪的文件。`make production-preflight`、
`make production-status`、`make production-deploy` 和
`make production-backup dir=/absolute/backup/path` 都会读取它；只有静态测试读取
可提交的 `.env.production.example`。

`WEKNORA_VERSION` 必须固定为明确版本且不能使用 `latest`。升级时先记录当前版本并完成
备份，再将该变量改为经过验收的新版本；不要让生产主机在重启时隐式拉取变化的镜像。
`PRODUCTION_BACKUP_DIR` 用于 `production-status` 判断最近一次带 `SHA256SUMS` 的有效备份，
应设置为受控、可持久保存的绝对路径。

## 4. 并发基线

实际部署只能运行一个 App 容器。该容器同时提供 API 和 Asynq Worker，生产基线为
Asynq `2`、Embedding `1`，并将三项 DocReader 限制都设为 `1`：

```dotenv
WEKNORA_ASYNQ_CONCURRENCY=2
CONCURRENCY_POOL_SIZE=1
DOCREADER_ODL_MAX_WORKERS=1
DOCREADER_MARKITDOWN_MAX_WORKERS=1
DOCREADER_PDF_RENDER_MAX_WORKERS=1
```

| 项目 | 生产值 | 说明 |
|---|---:|---|
| App 容器数 | 1 | 不得使用 `--scale app`。 |
| `WEKNORA_ASYNQ_CONCURRENCY` | 2 | 最多两个后台任务槽位。 |
| `CONCURRENCY_POOL_SIZE` | 1 | Embedding/模型调用串行，保护外部 Ollama。 |
| `DOCREADER_ODL_MAX_WORKERS` | 1 | OpenDocument 解析上限。 |
| `DOCREADER_MARKITDOWN_MAX_WORKERS` | 1 | MarkItDown 解析上限。 |
| `DOCREADER_PDF_RENDER_MAX_WORKERS` | 1 | PDF 渲染上限。 |

数据库 `system_settings` 中的 `asynq.concurrency` 优先于
`WEKNORA_ASYNQ_CONCURRENCY` 环境变量。该数据库设置存在时必须为 `2`；修改后重启
App。不要仅修改环境变量就假定有效并发已变更。

## 5. 首次上线与验收

先在生产主机完成环境文件配置，再按顺序执行：

```bash
make production-preflight
make production-deploy
make production-status
```

`production-deploy` 会先启动依赖、等待 PostgreSQL 就绪并校验数据库覆盖项，再启动 App。
启动后 `production-status` 会检查 App、PostgreSQL、Redis、DocReader、Ollama 模型与本机
可观测资源、文件系统容量、最近有效备份、待处理文档，以及每个 Asynq 队列的
pending/active/retry/archived 数量。验收时确认 App 容器数为 1、有效 Asynq 并发为 2 或
数据库设置为空、Embedding 为 1，并上传一份小文档验证解析、检索和问答。

## 6. 反向代理与网络

仅将前端监听在 `127.0.0.1:8088`，由企业既有 Nginx、Caddy 或网关终止 TLS 并转发
到该地址。不要将 `5432`（PostgreSQL）、`6379`（Redis）、`8080`（App API）或
`50051`（DocReader）直接暴露到公网；它们应保持内网或 Compose 网络可达。

Redis AOF 数据保存在 `redis-data` 命名卷；它和 PostgreSQL、`data-files` 同样属于
生产状态，升级、排障和清理时不得删除。Redis 密码仅通过真实生产环境文件提供。

## 7. 大文档与钉钉运行规则

- 一个文档在任一时刻只能有一个解析或重新解析任务；先等待该任务进入终态。
- 钉钉附件下载因权限失败时，按连接器的跳过项处理；不要重试整个同步，也不要为该附件排队解析。
- 已完成的文件已有切片和索引。恢复、重启或升级后先验证检索，不重新切片或重新解析。
- Ollama 高负载时保持 Embedding 为 1，记录延迟、CPU、内存和队列年龄，再决定是否扩大容量。

## 8. `processing` 卡住处置

发现文档长时间处于 `processing` 时，先执行：

```bash
make production-status
```

记录文档 ID、`processing` 年龄和操作时间，然后按固定顺序收集证据：App 日志、
DocReader 日志、Ollama 的健康/延迟/CPU 信息、Redis 队列状态。不要先刷新页面、重启
容器或再发起解析。

仅通过应用提供的任务取消路径取消该任务。确认文档和任务状态均已终止后，才允许对同一
文档执行一次重试；重试后继续观察状态与证据。已完成文档不在此流程中重新解析。

## 9. 备份、升级与回滚

备份到不存在或为空的绝对路径：

```bash
make production-backup dir=/absolute/backup/path
```

该命令生成 PostgreSQL 自定义格式备份、`data-files` 卷归档和 `SHA256SUMS`。PostgreSQL
中的向量索引（或外部向量库数据）与 `data-files` 必须同批备份。恢复已完成文档后，验证
检索结果，不执行重新解析。

升级窗口遵循以下八步：

1. 执行 `make production-preflight`，确认单 App 和有效并发。
2. 执行生产备份并校验 `SHA256SUMS`。
3. 记录当前镜像 tag、Git commit、配置 hash、数据库 `asynq.concurrency` 和队列深度。
4. 停止新的手工重新解析和定时数据源同步。
5. 等待队列排空；无法完成的任务只能通过应用取消路径终止，不能手工删除 Redis 键。
6. 更新已批准的镜像与真实 `.env.production`，再执行 `make production-deploy`。
7. 执行 `make production-status`，验证一份小文档以及两份大的钉钉表。
8. 验收后恢复定时同步；若需回滚，恢复上一镜像 tag 和生产配置。只有确认数据损坏时才恢复数据备份。

### 禁止命令

生产环境禁止 `docker compose down -v`、Redis flush、删除 Docker volume，或以删除队列
和重启容器代替应用取消流程。这些操作会破坏文件、索引或任务状态，且不是升级或回滚步骤。

## 10. 未来扩容边界

在 API/Worker 拆分、文档任务幂等性、去重入队、取消和关闭排空均已验证前，禁止把 App
扩为多副本。也禁止照搬 Helm 的 `app.replicaCount: 3` 示例；当前每个 App 副本都会启动
一个 Asynq 消费者。
